# Аудит чистоты V3

**Зона проверки:** только локальный прототип `webapp-mini-v3`.  
**Дата:** 2026-07-27.  
**Влияние на production:** отсутствует. Рабочей Mini App остаётся V2.

## Краткий вывод

V3 сейчас визуально работает как локальный прототип, но её код состоит из двух слоёв:

1. Активный прототип: `index.html`, `src/main.js`, `src/payment-config.js` и файлы в `src/css/`.
2. Заготовка будущей архитектуры: `src/api/`, `src/modules/`, `src/state/`, `src/ui/`, `src/mocks/` и `src/config.js`.

Эти слои пока не соединены. На этапе дизайна это нормально, но их нельзя объединять копированием кода из V2 или подключением всех блоков разом.

## Что реально запускается

Точка входа сейчас загружает только:

- `src/payment-config.js`;
- `src/main.js`;
- стили из `src/css/`.

Активный `main.js` управляет дизайн-прототипом, демонстрационной оплатой, настройкой ключа, экраном рефералов и локальной навигацией.

## Результаты аудита

### 1. Будущая архитектура пока не подключена к прототипу

`src/api/`, `src/modules/`, `src/state/`, `src/ui/`, `src/mocks/` и `src/config.js` не импортируются из `index.html` или `src/main.js`.

**Что это значит:** сейчас они не ломают прототип. Это фундамент для будущего подключения, а не второе работающее приложение.

**Что делаем:** пока сохраняем. Когда подключаем конкретный бизнес-блок, берём только его часть фундамента, проверяем локально, а затем в рамках того же блока завершаем или удаляем неиспользуемые части.

### 2. Активный контроллер слишком большой

`src/main.js` содержит несколько экранов и демонстрационные бизнес-сценарии в одном файле.

**Риск:** если начать добавлять API-вызовы прямо в него, получится та же конфликтная структура, от которой V3 должна уйти.

**Что делаем:** разделяем постепенно, только по бизнес-блокам и после согласования API-контракта:

- подписка и главная;
- ключи и настройка устройств;
- оплата;
- рефералы и QR;
- админка.

Пока дизайн меняется каждый день, не делаем большое механическое разделение файла.

### 3. Есть две папки со стилями

`src/css/` - активный слой стилей. `src/styles/` маленькая папка, которая не подключена из `index.html`.

**Что делаем:** не удаляем вслепую. После первой фиксации дизайна сравниваем её содержимое с `src/css/` и удаляем отдельной чистой правкой, если папка действительно стала не нужна.

### 4. Остались безопасные, но устаревшие ссылки на элементы экрана

Контроллер ещё ищет старые необязательные элементы:

- `setup-selected-val`;
- `btnDeviceGuideBanner`;
- `refStatsToggleText`;
- `btnScanQr`.

Большинство защищено проверками на отсутствие, поэтому страницу не ломают. Это следствие того, что макет менялся быстрее контроллера.

**Что делаем:** убираем каждую ссылку при чистке её собственного экрана до подключения API. Не создаём пустые элементы только ради того, чтобы заглушить код.

### 5. QR использует внешний сервис

Экран рефералов строит QR через `quickchart.io`.

**Что делаем:** заменяем до подключения API рефералов. Backend должен отдавать только ссылку, а V3 должна рисовать QR локально с проверенной встроенной библиотекой. На случай ошибки остаются видимая ссылка и действие «Скопировать».

### 6. В ассетах лежат исходники и варианты дизайна

`assets/candidates/` и `assets/PSwork/` - это дизайн-исходники, а не ошибки runtime. У ряда иконок также есть несколько вариантов PNG/SVG.

**Что делаем:** сохраняем, пока идёт дизайн. После фиксации дизайна составляем отдельную карту: используется в runtime, оставить как исходник, архивировать, удалить. Нельзя удалять дизайн-исходники внутри функциональной правки.

### 7. Данные прототипа намеренно демонстрационные

Платёжные реквизиты, данные пользователя, даты, ключи и статистика рефералов сейчас являются локальными примерами.

**Что делаем:** заменяем блок за блоком через явные контракты. Не переносим напрямую `main.js` или клиент V2.

## Правила перед подключением API

Для каждого блока:

1. Согласовываем API-контракт и состояния ошибок.
2. Сначала делаем соответствующий V3-адаптер с локальными mock-данными.
3. Проводим локальные проверки взаимодействий и статические проверки файлов.
4. Проверяем только изменённый блок на старый код, дубли стилей и лишние обработчики.
5. Подключаем backend только после приёмки.
6. Не начинаем следующий блок, пока текущий не стабилен.

## Безопасный порядок чистки

1. Навигация и общие помощники - уже в работе.
2. Экраны настройки ключей и их устаревшие обработчики.
3. Локальное построение QR до подключения рефералов.
4. Вынос демонстрационной оплаты перед подключением API оплаты.
5. Удаление старого слоя стилей после визуальной проверки.
6. Финальная инвентаризация ассетов перед первой release-сборкой V3.

## Что этот аудит не менял

- Не менялись V2, backend, сервер, БД, bot URL, Nginx, x-ui или runtime оплаты.
- Не удалялись дизайн-исходники, варианты картинок или неиспользуемые файлы.
- V3 намеренно остаётся локальной и исключённой из Git.
