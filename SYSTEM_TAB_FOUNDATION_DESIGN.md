# Mini App V3: фундамент вкладки «Система»

Дата: 2026-07-31  
Статус: согласовано владельцем, ожидает реализации

## Цель

Сохранить текущий дизайн вкладки «Система», но сделать её состояние честным, согласованным и готовым к последующему подключению административного API. На этом этапе используются только локальные mock-данные. Backend, сервер, Xray, база данных и production не изменяются.

## Единый снимок системы

Вся вкладка должна строиться из одного объекта `system snapshot`, содержащего:

- время формирования и время наблюдения сервером;
- общий статус;
- предупреждения;
- сервисы;
- серверы и их метрики;
- Xray, базу данных, резервные копии, Telegram-бот, платежи и очереди;
- технические версии;
- системные события.

Верхний статус вычисляется из содержимого снимка:

- `healthy` — предупреждений и критических ошибок нет;
- `degraded` — есть предупреждения, но основные сервисы доступны;
- `critical` — недоступен критический сервис;
- `unknown` — снимок ещё не получен.

Одна метрика не может иметь разные значения в разных карточках. Предупреждения формируются из того же снимка, а не из отдельного несвязанного массива.

## Состояния интерфейса

Вкладка поддерживает состояния:

- `loading` — первый снимок загружается;
- `ready` — новый снимок полностью отрисован;
- `refreshing` — показан последний подтверждённый снимок, сверху идёт обновление;
- `stale` — обновление не удалось, но последний подтверждённый снимок сохранён;
- `unavailable` — ни одного подтверждённого снимка получить не удалось.

Надпись «обновлено» появляется только после завершения всех частей снимка: обзора, сервисов, серверов, подсистем и событий. Старый поздний запрос не может перезаписать более новый результат.

Поиск и фильтрация системных событий имеют собственную последовательность запросов. Только последний запрос может менять список.

## Проверки подсистем

Кнопки проверки Xray, базы, бота и платежного обработчика:

- блокируются на время выполнения;
- показывают конкретное состояние действия;
- возвращаются в исходное состояние в `finally`;
- показывают отдельные сообщения об успехе и ошибке;
- не изменяют общий снимок без подтверждённого результата.

## Опасные действия

Перезапуск Xray и создание резервной копии остаются двухэтапными:

1. Пользователь открывает подтверждение.
2. После подтверждения отправляется одна операция с устойчивым `request_id`/idempotency key.

Требования:

- повторное подтверждение блокируется до завершения операции;
- один клик не создаёт несколько задач;
- polling имеет ограничение по времени и останавливается при успехе, ошибке, закрытии страницы или потере видимости;
- транспортная ошибка не показывается как подтверждённый провал серверной операции;
- результат операции отражается в журнале и инициирует фоновое обновление снимка;
- автоматический повтор mutating-запроса не выполняется.

На mock-этапе сохраняется тот же контракт без реального воздействия на Xray или базу.

## Безопасный рендеринг

Динамические серверы, предупреждения, сервисы, события и история резервных копий создаются DOM-элементами с `textContent`. Inline `onclick` и вставка будущих API-данных через HTML-строки удаляются.

Переход «Требует внимания → Серверы» должен вести на существующий блок. Кнопка «Подробнее» открывает только найденный сервер; неизвестный ID показывает понятную ошибку.

## API-граница на будущее

Локальный адаптер и будущий backend-адаптер должны возвращать одинаковую форму данных. Включение API не должно требовать изменения DOM-рендеринга или бизнес-логики вкладки.

Frontend не определяет права администратора. Будущий API обязан проверять роль на каждом системном маршруте. Публичная пользовательская сборка не должна содержать административную разметку и mock-данные.

## Локальные проверки

До завершения этапа проверяются сценарии:

- первый успешный снимок;
- обновление поверх последнего снимка;
- ошибка обновления с сохранением старых данных;
- ошибка первого снимка без ложного статуса «всё работает»;
- старый ответ приходит после нового и игнорируется;
- поиск событий не перерисовывается старым ответом;
- переходы из предупреждений ведут в существующие блоки;
- проверки четырёх подсистем разблокируют кнопки при успехе и ошибке;
- двойное подтверждение опасной операции создаёт одну задачу;
- polling завершается по успеху, ошибке и тайм-ауту;
- синтаксис JavaScript и целостность HTML ID.

## Не входит в этап

- подключение production API;
- реальные перезапуски Xray;
- реальные операции с базой или резервными копиями;
- Nginx, bot URL, VPN runtime и публикация;
- изменение согласованного дизайна;
- полное разделение большого `admin.js` на модули.

## Rollback

Изменения этапа ограничиваются frontend-файлами V3. Откат выполняется возвратом локального diff вкладки «Система»; runtime и пользовательские данные не затрагиваются.
